## v1.4.0 — incremental thinking emit on stable VS Code

**Symptom:** On stable VS Code (no `languageModelThinkingPart` proposal), thinking is only emitted at end-of-stream. Users see a blank chat pane for the entire generation, then a giant `` block appended at the end.

**Why it's deferred:** Real UX gap — every other major chat provider streams thinking progressively (ChatGPT, Claude, Copilot). The fork streams only at `[DONE]` or `finish_reason`. Worth a v1.4.0 release with manual testing on both stable and Insiders builds because the two render paths diverge.

**Files to change:** `src/sse.ts` only.

**Implementation sketch (~10 lines):**

```ts
// Current (v1.3.5): accumulate, emit on flush only.
if (thinking) thinkBuf += thinking;

// v1.4.0: emit per chunk, drop the dedup.
if (thinking) {
  thinkBuf += thinking;
  cb.onThinking(thinkBuf);
  thinkBuf = '';
}
```

Plus remove the `thinkBuf = ''` reset that currently happens at `finish_reason`/`[DONE]`/end-of-stream in `consumeSseStream`.

**Test plan:**
- Stable VS Code 1.134+: ask a long-running question (M3 with `thinking: adaptive`); confirm thinking streams into the chat pane in real time, not in one block at the end.
- Insiders build with `--enable-proposed-api=calvyntwh.calvyntwh-minimax`: confirm `LanguageModelThinkingPart` collapsible still works (regression check — the proposed-API path is already streaming).
- Cancellation: confirm partial thinking is preserved on stop (don't reset the buffer on abort).

## Audit findings — do not re-investigate

A 4-agent parallel audit on commit `f0b285b` (v1.3.5) returned 12 issues. After review, **10 were false positives** and **2 were real (both fixed in subsequent releases)**. This is the canonical list so future-you doesn't redo the same work.

### Real issues (fixed)

| ID | Finding | Fixed in |
|---|---|---|
| B3 | 200KB think-buffer overflow flushed to visible text | v1.3.4 (`src/sse.ts` 200_000 guard now routes to thinking with `[truncated]` marker) |
| R3 | Comment claimed `max_tokens` fallback that was never emitted | v1.3.4 (comment corrected) |
| R4 | Image mime detection ignored host's `part.mimeType` | v1.3.5 (`pickImageMime` honors host mime if it's in M3's supported set, falls back to byte sniff, surfaces error to user when both fail) |

### False positives — do NOT re-fix these

| ID | Audit said | Why it's wrong |
|---|---|---|
| B1 | "No `enabledApiProposals` — `vsce` will fail packaging" | We deliberately removed it so the extension can publish to the Marketplace. `vsce publish` has been verified to succeed. |
| B2 | "`reasoning_split` and `thinking` should be top-level fields, not in `extra_body`" | Per [platform.minimax.io/docs/api-reference/text-openai-api](https://platform.minimax.io/docs/api-reference/text-openai-api), MiniMax-specific fields go in `extra_body`. The audit didn't read the docs. |
| R1 | "`delta.reasoning_content` not parsed" | `reasoning_content` is a non-streaming-only field. M-series uses `delta.reasoning_details[]` during streaming. |
| R2 | "`tool_choice` never sent" | Server default is `'auto'`, which is what we want. Sending explicitly adds no value. |
| R5 | "`maxInputTokens` ≠ `contextLength` for M2.x" | Per-tier `maxInputTokens` reflects reserved overhead for system/tool messages. VS Code shows the smaller number for quota UI; that is correct. |
| R6 | "M2.x + `thinking:disabled` sent as-is" | Documented. README explicitly states M2.x ignores `thinking.type`. |
| R7 | "`finish_reason: tool_calls` returns immediately, late content dropped" | OpenAI spec: `tool_calls` is the terminal finish_reason; no content should follow. If MiniMax deviates, that's a model bug. |
| R8 | "Multi-line SSE `data:` fields not joined per spec" | MiniMax doesn't emit multi-line data. |
| H1 | "`engines.vscode: ^1.95.0` doesn't signal proposed-API requirement" | We need the lower bound for stable-build users. Vendored `.d.ts` are optional. |
| H2 | "Stale `package-lock.json`" | Auto-regenerated by `npm install`; freshness depends on the user's npm version, not the package's. |
| H5 | "No `extensionKind`, `qna`, `homepage`, `bugs`" | Marketplace polish. Not blocking. |

## Upstream issues to file

These are platform-level issues that the fork cannot fix. File them when the user has time, and link them from this doc so they don't get lost.

### Microsoft / VS Code

- **Copilot Chat prepends agent persona to all LM provider requests.** When a user picks a custom model (e.g., MiniMax M3 from this fork), Copilot Chat's host injects a "You are GitHub Copilot..." prompt before the user's actual message. The model then answers as "GitHub Copilot" instead of its real identity. Tracked behavior; no fix from a BYOK provider side. ([vscode-copilot-release#9523](https://github.com/microsoft/vscode-copilot-release/issues/9523))
- **Stable VS Code strips HTML from LM provider text parts.** The proposed `LanguageModelThinkingPart` is the only way to render thinking as a collapsible block. Tracking: vscode#246993 (in Backlog as of 2026-08). Until it lands, thinking on stable renders as inline text.

### MiniMax

- **M-series streams `` inline in `delta.content`** even with `reasoning_split: true`. The MiniMax docs claim reasoning is routed through `delta.reasoning_details[]` when `reasoning_split: true`, but in practice M3 also emits `<think>...</think>` tags inline. Cross-chunk token splitting makes this worse (markers can be split mid-word). Tracked at [MiniMax-AI/MiniMax-M3#28](https://github.com/MiniMax-AI/MiniMax-M3/issues/28) and vllm#45718.
- **M2.x `thinking: disabled` is silently ignored.** The parameter is accepted but the model always thinks. Documented; not a bug, but the silent ignore is surprising for users who explicitly opt out. ([platform.minimax.io/docs/api-reference/text-anthropic-api](https://platform.minimax.io/docs/api-reference/text-anthropic-api))

### Fork-specific follow-ups (low priority)

These are small cleanups that could be ported back from upstream if the fork ever pulls again:

- **Re-add `visibleModels` setting** (upstream has it; the fork doesn't). Power-user feature: hide models from the picker. ~20 lines.
- **Re-add China region switch commands** (upstream has `minimax.switchToGlobal` and `minimax.switchToChina`). The fork relies on the user editing `apiBaseUrl` directly. ~30 lines.
- **Map MiniMax error codes (1000/1004/1008/1026/1039) to `vscode.LanguageModelError` subclasses.** The fork surfaces them as text. ~30 lines, borrowed from upstream's `MiniMaxErrorMapper`.
- **Auto-recover on 401:** delete the bad key from `SecretStorage` and re-prompt for a new one. The fork currently just reports the 401 to the user; upstream clears and re-prompts. ~10 lines.

None of these are blocking for the target audience. Treat as a future polish pass if the user wants a more feature-complete fork.

## Maintenance expectations

Per the upstream-vs-fork diff (commit range `8e82fa2`..`main`):

- **Fork size:** 5 source files, 1,115 LOC + 288 LOC of vendored `.d.ts`. Zero runtime deps. `engines.vscode: ^1.95.0`.
- **Update cadence:** MiniMax rarely changes the OpenAI-compatible chat-completions shape. VS Code's LM provider API is stable since 1.95. Expect ~30 minutes/year to bump `engines.vscode` and re-test; ~1 hour/year to bump a model ceiling if MiniMax changes one.
- **What to do when upstream ships a fix:** fetch `upstream/main`, review the diff against this fork's patch (v1.3.5), and rebase the fork's `main` on top. The fork's `extra_body`-driven `buildBody` and the proposed-d.ts vendoring are the highest-friction rebase points; everything else should merge cleanly.
